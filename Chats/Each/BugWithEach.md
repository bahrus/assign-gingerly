## Diagnosis & Fix

### Root Cause

The key `"?.ariaControlsElements?.@each?.hidden =!"` ends with the toggle command (`=!`). In `assignGingerly.ts`, command handlers (`+=`, `=!`, `-=`, `Y=`) run *before* the general `@each` detection in the main assignment loop. As a result, the toggle handler parsed the LHS path parts as `['ariaControlsElements', '@each', 'hidden']` and fed them straight to `ensureNestedPath`, which treated `@each` as a literal property name and created an object at `target['ariaControlsElements']['@each']`. That is the source of the observed error/bug.

A second issue surfaced because `assignFrom` resolves RHS path strings before calling `assignGingerly`. For the pattern `"?.expanded"`, `assignFrom` passes the resolved boolean value (e.g., `true` or `false`) into `assignGingerly`. The old toggle handler only knew how to interpret string paths as the RHS, so it would misread a boolean `false` as a missing plain key and default the value to `true`, producing the wrong assignment even if `@each` were handled.

### Fix Applied

Changed `assignGingerly.ts` so the `=!` (toggle) handler:

1. Detects `@each` in the LHS path before falling back to `ensureNestedPath`.
2. When `@each` is present, it navigates to the iterable, then applies the toggle to each item via a new helper `applyToggleToEach`.
3. `applyToggleToEach` supports:
   - Resolved literal RHS values (booleans, numbers, etc. from `assignFrom`).
   - Path-string RHS values resolved against the original target (e.g., `"?.expanded"`).
   - Self-reference `"."` which negates the current property value on each item.
   - Nested `@each` paths.
   - `withMethods` and aliases.
4. Added a small helper `resolveValueToNegate` that handles both string paths and resolved literals, so the non-`@each` toggle path also works correctly with values resolved by `assignFrom`.

### Files Changed

- `assign-gingerly/assignGingerly.ts` — core fix (helpers + toggle handler).

- `assign-gingerly/tests/toggle-command.html` — added tests for `@each` toggle, resolved literal RHS, and the end-to-end `assignFrom` scenario.

## Follow-up Finding (hidden not toggling)

After the initial fix, the browser test showed the controlled `<section>` still had `hidden="until-found"` even though `expanded` became `true`.

### Root Cause of the Follow-up

The `plus-minus` feature config passes `withMethods` (`akaMethods: { "🔍": "querySelector" }`), so the toggle handler took the `evaluatePathWithMethods` branch when navigating to the iterable. For a single-segment path like `['ariaControlsElements']`, `evaluatePathWithMethods` returns the **container object** (`target`) and the last key (`'ariaControlsElements'`), not the value at that key. The code was assigning `current = result.target`, which left `current` as the `plus-minus` element instead of its `ariaControlsElements` array. Since an element is not iterable, `applyToggleToEach` was never called.

### Second Fix Applied

Updated `evaluatePathWithMethods` to track whether the final path segment was consumed as a method argument, then used that information in both the new toggle `@each` handler and the existing main `@each` handler:

```ts
const result = evaluatePathWithMethods(target, pathToForEach, value, withMethodsSet, permissionProcessor);
if (result.lastSegmentConsumed) {
  current = result.target;
} else if (result.isMethod) {
  const method = result.target[result.lastKey];
  current = typeof method === 'function' ? method.call(result.target, ...appendArgs) : method;
} else {
  current = result.target[result.lastKey];
}
```

- `lastSegmentConsumed`: the final segment was used as an argument to a previous method (e.g., `querySelectorAll?.my-element`), so `result.target` is already the iterable.
- `isMethod`: the final segment is a listed method, so the iterable is the method return value.
- Otherwise: the final segment is a property, so the iterable is `result.target[result.lastKey]`.

### Verified Behavior

After the second fix, clicking the expand/collapse buttons in `/demo/dev.html` correctly toggles the controlled section:

- Expand (`expanded=true`) → `hidden=false`
- Collapse (`expanded=false`) → `hidden=true`
- Expand again → `hidden=false`

## Conclusion / Reply to Bruce's Response II

No — the fix I applied is **specific to the `=!` (toggle) operator**. It does **not** automatically fix `+=`, `-=`, or `Y=` when those commands are combined with `@each`.

### Why the other operators are still affected

`assignGingerly.ts` processes command suffixes (`+=`, `=!`, `-=`, `Y=`) in a series of early `if` blocks, **before** the general `@each` detection in the main assignment loop. My changes only added `@each` awareness to the `=!` handler and fixed the `evaluatePathWithMethods` navigation so the iterable is resolved correctly. The `+=`, `-=`, and `Y=` handlers still use the old logic, so a key like:

```json
"?.ariaControlsElements?.@each?.hidden +=": 1
"?.ariaControlsElements?.@each?.hidden -=": "prop"
"?.ariaControlsElements?.@each?.style Y=": { "color": "red" }
```

would still be parsed as a literal path, `ensureNestedPath` would create an object property literally named `@each`, and the intended iteration would not happen.

### Should we fix them now?

That depends on whether your use cases actually need `@each` paired with those operators. At the moment:

- Your reported bug only uses `=!`.
- The existing test suite does not exercise `@each` with `+=`, `-=`, or `Y=`.
- The `el-maker.json` config for `plus-minus` does not use those combinations either.

If you want, I can extend the same `@each` handling to `+=`, `-=`, and `Y=` as a follow-up. It would be a similar pattern to what I did for `=!`: detect `@each` in the LHS path, navigate to the iterable, then apply the operation to each item. Let me know if you'd like me to proceed with that.

## Thoughts on Extending the Fix to `+=`, `-=`, and `Y=`

You're right — users will expect `@each` to compose with all the operators, and duplicating ~200 lines per operator would be bad. We should share logic.

### Proposed approach

Instead of adding a separate `@each`-aware handler for every command, refactor so that each command handler:

1. Parses the command and the LHS path.
2. Detects `@each` in the LHS path (one shared check).
3. If `@each` is present, calls a single shared helper: `applyCommandToEach(iterable, remainingPath, commandSuffix, value, options, permissionProcessor)`.
4. The shared helper:
   - Navigates to the iterable (using the same `evaluatePathWithMethods` fix already in place).
   - Walks the remaining path, handling nested `@each` recursively with one shared navigation routine.
   - At the leaf, builds a synthetic command key like `'?.hidden +=': value` and calls `assignGingerly(item, syntheticKey, ...)`.

By delegating the actual `+=`, `=!`, `-=`, `Y=` semantics back to the existing command handlers on the individual item, we reuse all the existing command logic and only need to write the iteration/navigation plumbing once.

### What this would touch

- `assignGingerly.ts`:
  - Extract the nested `@each` navigation logic currently in `applyToEach`/`applyToggleToEach` into a shared helper.
  - Add `applyCommandToEach`.
  - Refactor `applyToggleToEach` to use the same shared helper.
  - Modify the `+=`, `-=`, and `Y=` handlers to detect `@each` and dispatch to `applyCommandToEach`.
- `tests/toggle-command.html` and possibly new test files for `+=`/`-=`/`Y=` with `@each`.

### Scope estimate

This is roughly a **1-file refactor** in `assignGingerly.ts` plus tests. It should not add 200 lines per operator; the net addition should be modest because we'll replace the duplicated navigation in `applyToggleToEach` with the shared helper at the same time.

### Recommendation

Proceed with the refactor. It makes the behavior consistent across all operators, fixes the latent bugs, and keeps the code maintainable. Let me know if you want me to start on it.

Without this proposed feature, a developer needs to do the following.

See comments where I point out what this proposal is meant to improve:

```html
<div id=outerDiv itemscope>
    <div itemprop=user itemscope="user-card">
        <h2>User Profile</h2>
        <span itemprop="name"></span>
        <span itemprop="email"></span>
    </div>
</div>
```

```TypeScript
import 'assign-gingerly/object-extension.js';

// Define a manager class
class UserCardManager {
  element;
  name = '';
  email = '';
  
  constructor(element, initVals) {
    this.element = element;
    if (initVals) {
      Object.assign(this, initVals);
      this.render();
    }
  }
  
  render() {
    this.element.querySelector('[itemprop="name"]').textContent = this.name;
    this.element.querySelector('[itemprop="email"]').textContent = this.email;
  }
}

// Register the manager
customElements.itemscopeRegistry.define('user-card', {
  manager: UserCardManager
});



const vm = {
  ...
  user: {
    name: 'Alice',
    email: 'alice@example.com'
  } 
}

// The code below is what I want to improve.

// Use assignGingerly with the 'ish' property
assignFrom(outerDiv,
  {
    '?.querySelector?.[itemprop="user"]?.ish': '?.user'
  },
  {
    from: vm,
    withMethods: ['querySelector']
  }
);
```

I *think* with the code as above, the constructor of UserCardManager will be hit.  Do you agree?

## Feedback

### Confirming: Yes, the Constructor Gets Hit

Looking at `handleIshProperty.ts`, when `ish` is first set on an element:
1. The `ish` setter queues the value
2. If no manager instance exists, it calls `new config.manager(element, initVals)` with the queued value as `initVals`
3. On subsequent sets, it calls `assignGingerly(managerInstance, newValue)` to merge into the existing instance

So yes — `assignFrom(outerDiv, { '?.querySelector?.[itemprop="user"]?.ish': '?.user' }, ...)` would:
1. Resolve `vm.user` → `{ name: 'Alice', email: 'alice@example.com' }`
2. Navigate to the `[itemprop="user"]` element via querySelector
3. Set its `ish` property → triggers manager instantiation with `{ name: 'Alice', email: 'alice@example.com' }` as initVals

### The TODO Document You're Looking For

That's [LoopedSubstitutionRevisited.md](../../TODO/LoopedSubstitutionRevisited.md) — it discusses using `forEachKeyIn` to bind input elements by name pattern without repetition.

### Areas for Improvement — My Suggestions

The pain points are:
1. **Verbose LHS** — `'?.querySelector?.[itemprop="user"]?.ish'` is a lot to type
2. **Performance** — querySelector is slow (~3-17μs at scale), but this only runs once per `assignFrom` call
3. **Ceremony** — setting up `#[id]` + `withIds` for a one-off reference feels heavy

#### Suggestion 1: Implicit `ish` Resolution via `itemprop` Convention

What if `assignFrom` could recognize a convention: when a plain property key matches an `itemprop` element in the target's DOM, automatically route through `ish`?

```ts
assignFrom(outerDiv, {
    user: '?.user'  // if outerDiv has [itemprop="user"][itemscope], route via .ish
}, { from: vm });
```

This would require `assignFrom` to detect:
- Target has an element with `itemprop="user"` and `itemscope`
- The matched element has (or can have) the `ish` property
- Assign the resolved value through that element's `ish`

**Pro:** Zero-ceremony — just name the property.  
**Con:** Implicit magic — hard to understand without knowing the convention. Also mixes concerns (property name = DOM structure).

#### Suggestion 2: A `distribute` Option

A dedicated option that maps sub-object keys to DOM targets:

```ts
assignFrom(outerDiv, {}, {
    from: vm,
    distribute: {
        user: '[itemprop="user"]',  // querySelector, route through .ish
    }
});
```

Or with the proxy DX:

```ts
assignFrom(outerDiv, {}, {
    from: vm,
    distribute: {
        user: { qry: '[itemprop="user"]', via: 'ish' },
    }
});
```

**Pro:** Explicit, declarative, separates routing from assignment.  
**Con:** Another option to learn. Overlaps with what `withIds` + `#[x]` already does.

#### Suggestion 3: A Handler — `builtIns.distribute`

A handler that takes a sub-object and distributes its properties to child elements via `ish`:

```ts
assignFrom(outerDiv, {
    '?.querySelector?.[itemprop="user"] =>': {
        do: 'builtIns.distribute',
        resolve: {
            value: '?.user',
            via: 'ish'  // default
        }
    }
}, { from: vm, withMethods: ['querySelector'] });
```

The handler would:
1. Find the target element (LHS path)
2. Set `element.ish = resolvedValue` (triggering manager instantiation/update)

But this is essentially what the current code already does — just `'?.querySelector?.[itemprop="user"]?.ish': '?.user'` without the handler overhead.

#### Suggestion 4: Shorthand with `withIds` Auto-Query by `itemprop`

What if `withIds` supported a shorthand for itemprop elements?

```ts
assignFrom(outerDiv, {
    '#[user]?.ish': '?.user'
}, {
    from: vm,
    withIds: {
        user: { itemprop: 'user' }  // shorthand for qry: '[itemprop="user"]'
    }
});
```

This gives you:
- Cached WeakRef access (~10ns on repeat calls)
- Short LHS (`#[user]?.ish`)
- Clear intent (`itemprop: 'user'` in withIds)

And with `forEachKeyIn` for multiple sub-objects:

```ts
const $ = paths<VM>();

assignFrom(outerDiv, smoothOver({
    ...Object.fromEntries(
        ['user', 'address', 'preferences'].map(key => [
            `#[${key}]?.ish`, $[key]
        ])
    )
}), {
    from: vm,
    withIds: Object.fromEntries(
        ['user', 'address', 'preferences'].map(key => [key, { itemprop: key }])
    )
});
```

Hmm — still verbose.

#### Suggestion 5: `distributeByItemprop` — The Simplest Win

A single option that says "for each key in the source that matches an itemprop element with itemscope, route through ish":

```ts
assignFrom(outerDiv, {
    // other assignments...
}, {
    from: vm,
    distributeByItemprop: ['user']  // or true for all matching keys
});
```

This would:
1. For each key in the list, find `[itemprop="${key}"][itemscope]` in the target
2. Set `element.ish = vm[key]`
3. Use WeakRef caching internally (auto-ID for performance)

**DX with the proxy:**
```ts
const $ = paths<VM>();
assignFrom(outerDiv, {}, {
    from: vm,
    distributeByItemprop: smoothOver([$.user, $.address])
});
```

### My Recommendation

**Suggestion 5** (`distributeByItemprop`) is the simplest from a DX perspective for this specific pattern. But it's quite specialized.

If you want something more general, **Suggestion 4** (itemprop shorthand in `withIds`) composes with the existing `#[x]` system and doesn't add new concepts — just a convenient query shorthand.

### Questions

1. Is the pattern always `itemprop` + `itemscope` + `ish`? Or should this work for non-itemscope elements too?
2. Should the route always be through `ish`, or could it assign directly to a property on the element?
3. Is the performance concern about the first call (querySelector) or repeated calls? If repeated, `withIds` caching already handles it.

## Response to Human Response I

### The Expanded Vision

I see where this is going — you're building toward a system where:
1. **Inferencer** handles the "what property to set" question (value, display, eventType) based on element type
2. **`inferredAssignments`** handles the "find the right elements and route values" question based on DOM structure (itemprop, name, etc.)
3. **microDataJoin** could use inferencer to know which element type + attributes to use when rendering
4. **`beVigilant`** adds reactivity for dynamically added elements

This is a coherent layered architecture.

### On `inferredAssignments`

```ts
inferredAssignments: {
    byItemprop: ['user'],  // or true
    byName: ['firstName', 'lastName'],  // phase II
}
```

**`byItemprop` semantics:**

For each key in the list:
1. Find `[itemprop="${key}"]` within the target, but **outside any inner `[itemscope]`** (donut-hole scoping via `withScopePerimeter`)
2. Multiple elements with the same `itemprop` are valid (e.g., `<span itemprop="author">` repeated in a list)
3. For each matched element:
   - If it has `itemscope` → route through `.ish` (manager instantiation/update)
   - If it doesn't have `itemscope` → use inferencer logic (set `value`, `textContent`, `dateTime`, etc. based on element type)
4. Cache matched elements via WeakRef (keyed by itemprop name, supports multiple refs per name)

**`byName` (phase II):**

Same pattern but queries `[name="${key}"]` — for form elements. Uses inferencer to set the right property (`value`, `checked`, etc.).

### On `withScopePerimeter`

Good call — this is essential for itemprop queries. Without it, `querySelector('[itemprop="name"]')` from an outer `itemscope` would reach into inner itemscopes and grab the wrong element.

The utility is small (~15 lines) and general-purpose. Porting it here makes sense. It'd be used as:

```ts
// Find all [itemprop="user"] that aren't inside a nested [itemscope]
const candidates = target.querySelectorAll(`[itemprop="${key}"]`);
const matches = Array.from(candidates).filter(el => 
    withScopePerimeter(target, el, '[itemscope]')
);
```

### On Multiple Elements Per Itemprop

The WeakRef cache would be `Map<string, WeakRef<Element>[]>` rather than `Map<string, WeakRef<Element>>`. When assigning:
- If the value is a primitive (string, number, etc.) → set it on all matched elements (broadcast)
- If the value is an object and the element has `itemscope` → route through `.ish` on each
- If the value is an array → possibly distribute one item per element (1:1 mapping)?

Or keep it simple: always broadcast the same value to all elements with that itemprop. The microdata spec allows multiple elements with the same itemprop (they represent multiple values for that property), but in practice for display-binding, broadcasting makes sense.

### On Inferencer as a Submodule

Makes sense architecturally — inferencer knows which property to set on which element type. The `inferredAssignments` feature would import from it to handle the non-itemscope case (plain elements without managers). The dependency direction stays clean: inferencer has no runtime dependency on assign-gingerly.

### Implementation Phases

| Phase | Feature | Depends On |
|-------|---------|-----------|
| 1 | Port `withScopePerimeter` into this package | — |
| 2 | `inferredAssignments.byItemprop` with `itemscope` → `ish` routing | withScopePerimeter |
| 3 | Include inferencer as submodule | — |
| 4 | `inferredAssignments.byItemprop` without `itemscope` → inferencer routing | inferencer |
| 5 | `inferredAssignments.byName` (form elements) | inferencer |
| 6 | `beVigilant` (MutationObserver for new elements) | phase 2+ |

### Questions

1. **Should `withScopePerimeter` live in a shared utility module (e.g., `domUtils.ts`)?** It's useful for both this feature and potentially other DOM-walking logic in the package.
2. **For phase 1, should I start with just the `byItemprop` + `itemscope` → `ish` case?** That doesn't need inferencer and gives immediate value.
3. **For the WeakRef cache with multiple elements — broadcast to all, or distribute array elements 1:1?**
4. **Should I port `withScopePerimeter` now as a first step?**

builtIns.tree demo

The same launch summary as the itemscopeTree demo, built with builtIns.tree from the same response (data/launch.json). The API response is used as-is (only UI state is overlaid), stateless formatting comes from named pipes, the rocket card and links bar each get an itemscope manager as their view model, and the tree config itself is pure JSON (shown below the log).

What this demo exercises, and what's missing compared to itemscopeTree
  • Element specifications as [tag, pattern, children] tuples; patterns resolve against the key's value ('?.small' reads vm.patch.small).
  • Pipes: named functions used as path segments. The date is join: ['?.parseDate?.longUtc', ' UTC'] with parseDate: Date.parse and longUtc a preconfigured Intl.DateTimeFormat's format; core summaries are a pipe too.
  • Itemscope managers as view models: { tag: 'section', ish: 'rocket-manager' } attaches RocketManager to the rocket card (by registered name, so the config stays JSON; no itemscope attribute). The card's patterns read its getters ('?.heightLabel'). "Toggle units" sets rocket.ish.metric, whose setter calls ctx.rebind(): the card updates without a tree rerun, and the setting survives "Run again".
  • Async onAssigned: LinksManager marks the links "verifying…", awaits a simulated check, then "✓ verified". Tree binds right away and rebinds by itself when the promise settles.
  • Static children: the rocket card's heading and its three spec rows, all resolving against the card's manager.
  • Rebinding in place: every button re-runs the same tree with a new view model. The log reports how many of the previous elements were reused; only "Clear & rebuild" creates new ones.
  • Null values: keepNullish keeps the details paragraph when details is null, and a '??' ternary chain shows the placeholder.
  • $parent: the status badge hangs off the success key and reads its sibling upcoming from the enclosing view model, via ' ?=' ternaries (['$parent?.upcoming', 'Upcoming', ['?.', 'Success', 'Failure']]).
  • Arrays, by composition: Tree doesn't do arrays yet, so the links, crew and core lists put a builtIns.manageTemplateList handler key inside the <ul>'s pattern. That handler runs fire-and-forget, so the lists fill in just after the tree.

Not covered, compared to the itemscopeTree demo:

  • Managers don't render DOM: structure stays in the tree config.
  • No microdata (itemscope/itemprop), by design.
